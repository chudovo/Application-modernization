# Case 05: Entity Framework 6 to EF Core on an existing database

The data layer of an order desk, written with Entity Framework 6 Code First, and the same data layer on EF Core 10.
The SQL Server database is not changed: same tables, same columns, same rows. Only the library that talks to it is
replaced.

One file of 17 scenarios is compiled against both data layers and run against a real SQL Server. Each test starts from
a fresh copy of the database exactly as Entity Framework 6 created it.

| | Before | After |
|---|---|---|
| Library | Entity Framework 6.5 | EF Core 10 |
| Runtime | .NET 10 (EF6 has run on modern .NET since 6.3) | .NET 10 |
| Mapping | conventions and a few attributes | written out to match the existing tables |
| Related data | lazy loading through virtual properties | `Include` or a projection per query |
| Date functions | `DbFunctions.TruncateTime` | `DateTime.Date` |
| Raw SQL | `Database.SqlQuery<T>` with `SqlParameter` | `Database.SqlQuery<T>` with an interpolated string |
| Migration history | `__MigrationHistory` | `__EFMigrationsHistory`, starting with an empty baseline |
| SQL client | System.Data.SqlClient | Microsoft.Data.SqlClient |

## Layout

```
database/legacy-schema.sql     the schema as EF6 Code First Migrations created it, generated by before/tools/ScriptDatabase
database/legacy-data.sql       rows as the old application wrote them
scenarios/                     17 scenarios and the database helper, shared by both test projects
before/src/OrderDesk.Data/     entities, context and OrderStore on Entity Framework 6
before/tests/                  the scenarios, plus one test of behaviour only EF6 has
after/src/OrderDesk.Data/      the same on EF Core, with the baseline migration
after/tests/                   the scenarios, plus schema checks and one test of behaviour only EF Core has
```

## Run it

You need the .NET 10 SDK and a SQL Server. With Docker:

```bash
docker run -d -e ACCEPT_EULA=Y -e MSSQL_SA_PASSWORD=Local_dev_only_1 -p 14330:1433 mcr.microsoft.com/mssql/server:2022-latest
dotnet test before/tests/OrderDesk.Scenarios
dotnet test after/tests/OrderDesk.Scenarios
```

To use another server, set `ORDERDESK_SQL` to its connection string. The tests create and drop their own databases.

## What is verified, and what is not

| Check | Where | Result |
|---|---|---|
| 17 scenarios against Entity Framework 6 | CI, SQL Server 2022 | 17 / 17 |
| 17 scenarios against EF Core 10 | CI, SQL Server 2022 | 17 / 17 |
| EF Core model equals the existing schema: columns, types, keys, foreign keys, indexes, names | CI | equal |
| Baseline migration changes no table, existing data readable afterwards | CI | passes |
| Committed schema script equals what EF6 generates for the model | CI | equal |

Not verified:

- **Performance.** No query timings were compared. The number of round trips changes (see lazy loading below), the
  effect on a real workload was not measured.
- **Both versions running side by side.** In a rollout the old and the new application often write to the same
  database for a while. The schema is untouched, so this should work, but no test runs them concurrently.
- **Other databases and features.** SQL Server only. No EDMX model, no stored procedure mapping, no table-per-type
  inheritance, no spatial types. Each of those has its own migration story.
- **Async.** Both versions keep the synchronous API of the original.

## The existing database

[`database/legacy-schema.sql`](database/legacy-schema.sql) is not written by hand. It is the script Entity Framework 6
Code First Migrations produces for the model in `before/`, and CI regenerates it to check that it has not drifted.
It shows what EF6 decided by convention:

```sql
CREATE TABLE [dbo].[Orders] (
    [Id] [int] NOT NULL IDENTITY,
    [CreatedUtc] [datetime] NOT NULL,
    [Total] [decimal](18, 2) NOT NULL,
    [RowVersion] rowversion NOT NULL,
    [Customer_Id] [int] NOT NULL,
    CONSTRAINT [PK_dbo.Orders] PRIMARY KEY ([Id])
)
CREATE TABLE [dbo].[TagOrders] (
    [Tag_Id] [int] NOT NULL,
    [Order_Id] [int] NOT NULL,
    CONSTRAINT [PK_dbo.TagOrders] PRIMARY KEY ([Tag_Id], [Order_Id])
)
CREATE INDEX [IX_Customer_Id] ON [dbo].[Orders]([Customer_Id])
```

## What EF Core assumes differently

Each row was measured by removing that part from the finished EF Core version and running the tests.

| Removed from the EF Core version | Result |
|---|---|
| All relationship and table mapping (EF Core conventions only) | 14 of 17 scenarios fail: `Invalid column name 'CustomerId'`, `Invalid object name 'OrderTag'` |
| `Include` in `GetOrder` | 6 of 17 scenarios fail with `NullReferenceException` |
| The decimal conversion | 1 scenario fails: 19.999 is stored as 20.00 instead of 19.99 |
| `HasColumnType("datetime")` | all 17 scenarios pass, the schema checks fail |
| Key, index and constraint names | all 17 scenarios pass, the schema checks fail |

**Names.** EF6 named the foreign key column `Customer_Id` and the join table `TagOrders` with `Tag_Id` and `Order_Id`.
EF Core looks for `CustomerId` and `OrderTag` with `OrdersId` and `TagsId`. The mapping is in
[`OrderDeskContext.cs`](after/src/OrderDesk.Data/OrderDeskContext.cs).

**Lazy loading.** The EF6 code reads an order and touches `order.Customer.Name`; the customer loads on first access.
In EF Core the property is `null`. Every such place needs an `Include` or a projection. EF Core has a lazy loading
package, but turning it on to avoid the work keeps the hidden queries.

**Decimals are rounded, not cut off.** A value with three decimals written to a `decimal(18,2)` column: EF6 stores
19.999 as 19.99, EF Core stores 20.00. No exception either way. The EF Core version keeps the old behaviour with one
value converter, because a library upgrade must not change money. Whether cutting off is what the business wants is a
separate decision.

**The last two rows are the dangerous ones.** With `datetime` left as EF Core's default `datetime2`, or with EF Core's
default names for keys and indexes (`IX_Orders_Customer_Id` instead of `IX_Customer_Id`), every scenario passes. The
problem appears later, in the first real migration, which then tries to alter columns and rename or drop objects that
do not exist under those names. [`SchemaTests.cs`](after/tests/OrderDesk.Scenarios/SchemaTests.cs) compares the EF Core
model with the catalog of the existing database line by line and fails on any difference.

## One difference in the other direction

Order 1 was created at 09:15:00.123. Looking it up by exactly that time finds nothing with EF6 and finds it with
EF Core. The column is `datetime`; EF6 sends the value as `datetime2`, and SQL Server (compatibility level 130 and
later) converts the stored value to 09:15:00.1233333 before comparing. EF Core, with the column mapped as `datetime`,
sends a `datetime` and the comparison is exact.

So the upgrade fixes a lookup that silently never worked for times with milliseconds. That is still a change in
behaviour, and it is recorded as one test per version
([EF6](before/tests/OrderDesk.Scenarios/Ef6Behaviour.cs), [EF Core](after/tests/OrderDesk.Scenarios/EfCoreBehaviour.cs))
instead of a shared scenario.

## Migrations: the baseline

The tables exist, so the first EF Core migration must not create them. `dotnet ef migrations add Baseline` generates
a migration full of `CREATE TABLE`; its `Up` and `Down` were emptied
([`Migrations/`](after/src/OrderDesk.Data/Migrations)). Applying it only writes one row to `__EFMigrationsHistory`.
The model snapshot generated next to it describes the existing database, and every later migration is a difference
from that snapshot. The table `__MigrationHistory` of EF6 is left in place.

## Notes

- `TrustServerCertificate=True` is read by both SQL clients. The connection string builder of the new client writes
  it as `Trust Server Certificate`, which System.Data.SqlClient rejects with `Keyword not supported`. If both versions
  read the same configuration during a rollout, keep the spelling without spaces.
- `dotnet ef dbcontext scaffold` generates a context from the database and is a quick way to get all the names right.
  Here the mapping is written by hand so that the entity classes stay the ones the application already uses; the
  schema test is what proves it correct.
